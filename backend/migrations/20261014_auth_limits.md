# Auth 요청 제한 공유 테이블

`20261014_auth_limits.sql`은 검토 후 운영자가 수동 적용하는 MySQL DDL이다. 애플리케이션에서 실행하지 않는다.

1. 대상 MySQL 버전, schema, 물리 테이블명/대소문자, InnoDB 사용과 백업·복구를 확인한다.
2. 격리된 동일 버전 MySQL에 SQL을 적용하고 두 독립 애플리케이션의 최초 bucket 생성 경합,
   예약 상한, 실패 기록 커밋/업무 롤백, 동시 SMTP 발급, 잠금 타임아웃·교착 상태를 검증한다.
3. 기존 `auth_limit_bucket`이 있으면 CREATE를 재실행하거나 덮어쓰지 말고 SHOW CREATE TABLE과
   컬럼·PK·인덱스를 대조한다. DDL은 MySQL에서 암묵적으로 커밋되므로 트랜잭션 롤백을 기대하지 않는다.
4. 운영자 검토 후 테이블만 먼저 생성하고 `ddl-auto=validate`, SQL `never`로 신버전을 배포한다.
   구버전은 제한을 우회하므로 외부 트래픽을 구버전에 계속 보내는 혼합 배포는 허용하지 않는다.
5. 모든 인스턴스는 같은 primary DB/schema, 같은 제한 설정 및 UTC DB 세션을 사용한다.
   JDBC URL의 `connectionTimeZone=UTC&forceConnectionTimeZoneToSession=true` 또는 관리되는 세션 설정으로
   `@@session.time_zone`을 확인한다. 읽기 복제본에 제한 쿼리를 보내지 않는다.

롤백: 신버전 트래픽을 중지하고 검토한 이전 버전으로 복귀할 수 있다. 기존 USER/토큰 데이터에는
DDL 변경이 없다. 제한 테이블은 보존한다. 즉시 DROP하거나 제한 기록을 초기화하면 보호가 사라진다.
구버전 복귀 시 외부 요청 제한 등 대체 보호 없이 공개 auth 트래픽을 재개하지 않는다.

보존: 코드에 자동 삭제/스케줄러를 추가하지 않았다. 제한 기록과 만료된 인증/재설정 이력은
운영자가 보존 기간·최대 실행 시간·백업을 확정한 뒤 별도로 검토한 작은 배치로 정리한다.
bucket의 updated_at 인덱스를 사용하고, 최소 보존 기간은 모든 요청/실패/차단 window와 최대 처리 시간보다
길어야 한다. 활성 제한을 지우거나 배포 시 테이블을 비우지 않는다.
