# 채팅 메시지별 읽음 확인 전환

이 문서는 문제 1(참여 상태 덮어쓰기)과 문제 3(읽음 정합성)의 수동 배포 절차다.
운영 DB에 자동 적용하지 않는다. 실제 MySQL 적용·잠금·성능은 별도 격리 검증이 필요하다.

## 변경 이유와 호환성

- `CHAT_MESSAGE.is_read BOOLEAN NOT NULL DEFAULT FALSE` 한 컬럼을 추가한다. 메시지·방·참여자 ID와 본문은 유지한다.
- 두 명으로 구성된 기존 방에서 메시지당 수신자는 한 명이다. 읽음은 그 수신자가 확인한 정확한 메시지 ID 집합으로 저장한다.
  시간 또는 최대 ID 이하를 일괄 읽음 처리하지 않으므로, A의 지연 커밋 중 B만 확인해도 A는 미읽음으로 남는다.
  생성 시각이 같거나 WebSocket 전달 순서가 바뀌어도 다른 ID의 읽음 상태를 이어받지 않는다.
- `POST /api/chat/rooms/{roomId}/read`에 `{"messageIds":[42,43]}` 본문이 필요하다.
  1~100개의 양수 ID를 받으며 중복은 제거한다. 모두 해당 방의 상대 메시지여야 하고, 잘못된 ID가 하나라도 있으면 전체 요청을 거절한다.
  인증·참여 권한을 먼저 검사한다. 빈/누락/잘못된 본문은 400이고 나간 참여자는 기존 403이다.
  성공은 기존 HTTP 200, ApiResponse의 data=null이다. 목록·메시지·STOMP 응답 필드와 정렬은 그대로다.
- 프론트의 관련 API/hook은 조회·수신 데이터를 렌더링한 뒤 상대의 메시지 ID만 확인한다.
  조회 실패·빈 목록·자기 메시지는 확인하지 않는다. 성공 후 현재 방의 미읽음 수를 재조회하며 무조건 0으로 만들지 않는다.
  이 확인은 클라이언트의 수신 확인이지 사람이 실제 내용을 읽었다는 증명은 아니다.
- 기존 `last_read_at`은 확인한 메시지 중 가장 나중 시각의 단조 증가 보조 정보로 유지한다.
  읽음 판정·미읽음 수에는 사용하지 않는다. 날짜 정밀도나 시계 차이가 메시지별 읽음에 영향을 주지 않는다.

## 잠금과 격리 수준

낙관적 잠금은 참여자 version 컬럼과 충돌 재시도 계약이 추가로 필요하다. 부분 UPDATE만 사용하면
오래된 권한 스냅샷과 방 사이의 pin 개수 검사까지 함께 보호하지 못한다. 기존 USER 잠금에 참여자 잠금/refresh를
결합하여 추가 참여자 스키마 없이 상태 변경을 직렬화하고, 읽음 시각에만 조건부 UPDATE를 함께 사용한다.
메시지별 확인은 방 전체 송신을 직렬화하지 않아도 지연 커밋을 구분하며, 읽음 범위용 최대 ID의 가정도 필요 없다.

참여자 쓰기(읽음/설정/나가기)는 USER → 자신의 CHAT_ROOM_MEMBER → 확인할 CHAT_MESSAGE ID 오름차순으로 잠근다.
USER 잠금은 기존 고정 최대 2개 제한을 방 사이에서도 직렬화한다. 다른 참여자의 USER/멤버 행은 잠그지 않는다.
이전 영속성 컨텍스트 객체를 그대로 신뢰하지 않고 잠금 획득과 함께 참여자 상태를 refresh한다.
반복 호출은 같은 트랜잭션의 잠금과 미커밋 변경을 유지한다. 읽음 시각은 DB의 조건부 UPDATE로도 역행을 거절한다.

MySQL REPEATABLE READ에서는 참여자 refresh·확인할 메시지 조회·현재 고정 목록 조회에 locking/current read를 사용한다.
정확한 ID만 확인하므로 다른 메시지의 지연 커밋을 기다리거나 읽음 범위에 포함시킬 필요가 없다.
H2의 RR은 선행 스냅샷 뒤 삽입된 행을 FOR UPDATE로도 숨기거나 경합 갱신을 롤백할 수 있다.
테스트는 이 차이에서 권한/읽음을 추정하지 않고 거절·롤백한 뒤 새 트랜잭션에서 재시도하는 것을 확인한다.
H2 통과가 InnoDB의 실제 current read·잠금 대기·데드락 검증을 대신하지 않는다.

## 적용 전 점검과 순서

1. DB/schema/버전, 실제 테이블 대소문자와 기존 DDL·행 수를 확인한다. 모든 방에 정확히 두 참여자가 있고
   메시지 sender가 그 방 참여자인지, FK/NOT NULL이 정상인지 읽기 전용으로 확인한다. 불일치가 있으면 중단한다.
2. 전체 DB의 일관된 백업을 격리 DB에서 복구 검증한다. 메시지 ID별 종전 읽음 판정도 안전하게 보관한다.
3. 모든 채팅 쓰기·연결과 진행 중 트랜잭션을 중지·drain한다. 구버전/신버전 혼재 배포는 허용하지 않는다.
4. 동일 버전 격리 MySQL에서 SQL·검증·복구를 먼저 실행한다. 큰 테이블의 ALTER/UPDATE 잠금·로그·소요 시간을 측정한다.
5. 운영자가 stop-on-error 방식으로 `.sql`의 ALTER를 한 번 적용하고, 별도 UPDATE 트랜잭션을 실행한다.
   UPDATE 실패 시 명시적으로 ROLLBACK한다. DDL은 그 ROLLBACK으로 취소되지 않는다.
6. 전환 UPDATE는 기존 `sent_at <= last_read_at` 표시 결과를 메시지별 값으로 옮긴다.
   과거의 잘못된 읽음 여부는 실제 수신 증거가 없으므로 복원하지 않는다. 기존 원시 시각은 수정하지 않는다.
   새 버전 쓰기가 시작된 후에는 이 UPDATE를 재실행하지 않는다. 개별 확인 결과를 timestamp 범위로 덮어쓸 수 있다.
7. 모든 메시지·방·참여자 행 수/ID/FK/본문과 종전/전환 읽음 판정을 대조한다.
   새 서버·새 프론트를 함께 시작하고 재접속한다. 기본/prod는 validate·SQL never를 유지한다.

## 롤백

- 새 쓰기 시작 전: 구버전을 재개하려면 쓰기를 멈춘 채 백업/원본과 대조한다. 추가 컬럼을 무조건 DROP하거나 전체 DB를 덮어쓰지 않는다.
- 새 쓰기 시작 후: 다시 쓰기를 중지하고 메시지별 읽음 정보를 백업한다.
  메시지별로 띄엄띄엄 확인한 집합은 하나의 timestamp로 손실 없이 되돌릴 수 없다.
  구버전으로 단순 복귀하면 미확인 메시지가 읽음 처리될 수 있으므로, 별도 복구 검토 또는 forward fix가 필요하다.

## 격리 MySQL에서 배포 전 실행할 검증

- RR에서 오래된 managed 참여자/스냅샷을 만든 뒤 다른 연결의 나가기·읽음·설정과 교차 실행한다.
  나가기 후 403(충돌 시 기존 409), is_left/left_at 보존, 읽음 시각 단조 증가와 pin 최대 2개를 확인한다.
- A 미커밋 → B 커밋 → B만 조회·확인 → A 커밋에서 A 미읽음 1개와 B 읽음을 확인한다.
- 동일 DATETIME, 역순 확인, 읽음 중 신규 전송, 잘못된 ID 혼합 요청, 다른 방 ID, rollback 후 재시도를 확인한다.
- 두 JVM에서 같은 요청을 교차하고 한 JVM 종료/lock timeout 시 원자적 rollback과 권한 유지 여부를 확인한다.
  JVM 간 Simple Broker 메시지 중계 문제는 이번 변경으로 해결되지 않는다.
- 익명 POST/COMMENT senderId·상대 프로필 마스킹, 방 재사용·나가기 정책, 2,000 코드 포인트 제한과 기존 정렬을 회귀 확인한다.
