# P0 실행 전 공유 실행기 변경 보고

2026-10-23 (Asia/Seoul). 사용자 승인에 따라 P0 8개 실행을 준비했다.
실행 전 필수 확인에서 아래 충돌을 확인하여 자원을 만들거나 테스트를 시작하지 않았다.
공유 실행기·fixture·서비스 코드는 변경하지 않았으며 이 보고서만 추가했다.

## 현재 실행기를 그대로 사용할 수 없는 이유

| 확인된 코드 | 현재 동작 | 이번 승인 조건과 충돌 |
| --- | --- | --- |
| `frontend/e2e/run.cjs:157~166` | cleanup에서 소유 컨테이너에 `docker rm --force --volumes` 실행 | 신규 자원 삭제 미승인 |
| `frontend/e2e/run.cjs:278~282` | Playwright 종료 후 `E2eDatabase clean`으로 모든 fixture 행 삭제 | 결과 DB를 보존하려면 생략 필요 |
| `frontend/e2e/fixtures.cjs:16~20` | 매 테스트 전 reset, 종료 후 clean | 후속 사례가 앞 사례의 검증 행을 지움 |
| `backend/src/e2e/java/e2e/E2eDatabase.java:105` | reset도 내부적으로 전체 테이블 clean을 먼저 수행 | 기존 reset을 초기화 전용 동작으로 간주할 수 없음 |

자원 삭제와 fixture 행 삭제는 구분한다. 이번 제안은 컨테이너·스키마·계정뿐 아니라
실행 결과 DB 행·업로드도 보존하여 사후 검토가 가능하도록 하는 안이다.
기존 실행기는 finally와 종료 신호에서도 삭제를 수행하므로 성공 경로만 우회해서는 충분하지 않다.
DB 저장소가 tmpfs이므로 보존 대상 컨테이너를 stop/restart하는 것도 피한다. 종료 후 실행 상태를 유지한다.

## 적용 전 보고하는 구체적 변경 범위

| 공유 파일 | 제안 변경 | 기존 실행에 대한 영향 |
| --- | --- | --- |
| `frontend/e2e/run.cjs` | 명시적 `--retain-resources` 모드 추가. Playwright에 전달하기 전에 이 인자를 분리. 새 실행 소유 자원만 생성하고 해당 모드에서는 모든 종료 경로에서 Docker 삭제·DB clean을 생략. 새 빈 DB의 seed를 한 번 수행. 자체 기동한 React/Spring/제어 프로세스는 종료하고 DB 컨테이너는 실행 상태로 유지. run.json에 모드·자원명·UUID·보존 여부·실패 단계를 기록 | 옵션 없는 기존 실행의 기본 동작은 유지. 이번 P0 명령에는 보존 옵션을 반드시 사용 |
| `frontend/e2e/fixtures.cjs` | 위 모드에서는 테스트 전 reset/종료 후 clean을 호출하지 않음. 기존 A/B/admin context와 증거 수집·외부 요청 차단은 재사용. 테스트별 생성 대상 ID로 사례를 격리 | 기존 일반 모드의 테스트별 reset/clean은 유지 |
| `backend/src/e2e/java/e2e/E2eDatabase.java` | 기존 소유권/UUID/권한 검사를 유지한 `seed` 동작 추가. 모든 테이블이 빈 상태일 때만 기본 계정·기준정보를 삽입하며 DELETE/TRUNCATE/DROP을 실행하지 않음. 보존 모드에서는 clean/reset 요청을 명시적으로 거절. 신고 처리시각·익명 댓글/번호·생성시각·이미지 정리 상태 등 P0에 필요한 비밀정보 없는 읽기 전용 snapshot 확장 | 기존 prepare/reset/clean/snapshot 계약은 일반 모드에서 유지. E2E source set에만 해당하며 배포 코드·스키마 변경 없음 |
| `frontend/e2e/runner.test.cjs` | 성공/실패/종료 신호에 적용할 보존 정책, 인자 분리, 보존 모드의 clean/reset 차단을 DB/Docker 없이 검증할 안전 검사 추가 | 인증·Calendar 업무 테스트를 실행하지 않음 |

삭제 명령을 가로채는 임시 셸, 런타임 소스 치환, 공통 실행기 복사본으로 우회하지 않는다.
기존 `community-report.spec.cjs`, `chat.spec.cjs`, `auth-boundaries.spec.cjs`와
`lib/flows.cjs`는 변경 없이 참고·재사용하고 담당 전용 P0 spec/helper를 새로 추가하는 안을 우선한다.
P0 테스트에는 다른 담당자의 설문·Matching·Calendar 업무 흐름을 포함하지 않는다.
설정·빌드 경로와 포트를 그대로 쓰므로 실행 시간도 다른 팀 E2E와 겹치지 않게 해야 한다.

## 보존 모드 승인 후 검증 순서

1. 공유 파일에 위 한정 변경을 적용하고 DB/Docker 없는 안전 검사를 먼저 수행한다.
2. P0 전용 테스트 선택과 삭제 없는 모든 종료 경로를 검토한다. 운영·공통 인증·로그아웃 정책은 변경하지 않는다.
3. 사용자가 승인한 새 컨테이너/스키마/계정 각 1개와 격리 업로드 경로만 만든다.
   기존 보존 자원은 열람·접속·변경하지 않는다. 포트 점유 시 기존 프로세스를 건드리지 않고 중단한다.
4. P0 ①~⑧을 실행한다. HTTP·STOMP·DB·파일 근거 및 기대값 오류/실제 결함/fixture 실패를 분리한다.
   실제 결함은 원인·재현·영향·최소 수정 범위를 보고하고 서비스 수정 전 확인을 받는다.
5. 자체 기동한 앱 프로세스를 종료하고 새 MySQL 컨테이너·DB·계정·업로드·증거는 보존한다.
   P1과 자원 삭제는 별도 승인 전 진행하지 않는다.

## 현재 상태

P0 ① 게시글/이미지, ② 댓글/답글/좋아요/내 활동, ③ 신고 처리, ④ 채팅방,
⑤ 실제 STOMP, ⑥ 읽음/복구, ⑦ 관리자 권한/제재/삭제, ⑧ 대시보드 모두 **미실행**이다.
서비스 FAIL로 분류하지 않는다. 실제 HTTP 0건, STOMP 연결 0건, DB 접속 0건, 신규 자원 0개다.
기존 분석의 초안 유실·저장 후 재조회 실패 위험은 실제 재현 전이며 이번에 새로 발견한 실제 결함으로 보고하지 않는다.

필요한 확인은 **위 4개 공유 파일의 보존 모드 한정 변경 승인**이다.
새 자원의 생성·사용 및 P0 실행 승인은 이미 받은 것으로 유지하며 다시 요청하지 않는다.
이 확인이 필요한 근거는 사용자의 조건 5번(공통 실행기·공유 파일 변경 전 보고)과
조건 3번(신규 자원 삭제 미승인)이다.
