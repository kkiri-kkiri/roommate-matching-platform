### 현재 상황의 해결 절차 — 조사 중 실행하지 않음

현재 전시회 데이터에는 복구할 문구 차이가 없으므로 **DB UPDATE나 백업 import가 필요 없다.**
후속 조치가 승인되면 다음 순서로 실행 환경만 바로잡으면 된다.

1. 이 조사 증거, 기존 `server.json`, 전시회 시작 로그를 새 경로에 보존한다.
   기존 백업과 로그를 덮어쓰지 않는다.
2. 당시 실제 8080 소유 프로세스·시작 시각을 다시 확인하고 IntelliJ에서 해당 백엔드 실행을 종료한다.
   조사 당시 PID 4624였다. 향후에는 PID를 고정해 사용하지 않는다.
3. 23832의 과거 기록과 실제 프로세스를 구분한 뒤 전시회 실행기의 `Stop`으로 남은 실행 기록을 정리한다.
   이 명령은 현재 IntelliJ 백엔드를 대신 종료하지 않으므로 2단계가 별도로 필요하다.
4. 기존 전시회 실행기의 `Start`로 서버를 시작한다. `Create`, `Bootstrap`, `Apply`, `TextApply`는 필요 없다.
5. 새 PID와 실제 8080 LISTEN 소유권, JDBC 연결 또는 TCP/MySQL 세션의 DB명을 함께 확인한다.
   `Status` 출력만으로 연결 확인을 끝내지 않는다.
6. 공개 목록 API에서 최신 닉네임과 글을 확인하고 프론트를 새로고침한다.
   로그인 세션이 남아 있다면 전시회 JWT 키에 맞춰 다시 로그인한다.

실행기의 `Status`가 PID 생존·시작 시각·포트 소유권을 검증하고, 기록된 DB와 실제 연결 확인을
구분하도록 보완하면 같은 오해를 줄일 수 있다. 이번에는 요청 범위에 따라 코드를 수정하지 않았다.

### 향후 실제로 일부 문구가 손상된 경우

전체 SQL 백업을 덮어쓰면 이후의 댓글·읽음 상태·좋아요 등 시연 중 변경을 잃을 수 있다.
현재 건에는 실행하지 말고, 실제 문구 차이가 확인된 경우에만 별도 검토한다.

- 전시회 DB와 대응하는 manifest/journal을 새 백업 경로에 함께 보존하고 서버를 정지한다.
- 기존 `TextPreview`/`--refresh-text`로 ID·소유자·출처 지문 및 변경 문구를 검토한다.
  출처·지문이 달라 SKIP이면 강제로 journal을 다시 서명하거나 새 기준으로 편입하지 않는다.
- 검토된 경우에만 정확한 preview token으로 텍스트 갱신을 수행한다.
  허용 열은 `user_profile.nickname`, `community_post.title/content`,
  `community_comment.content`, `chat_message.content`뿐이다.
- 기존 도구가 지문 불일치로 거부하면 별도 복구안을 만든다. 백업/현재 값/확정 문구를
  ID·소유자·부모 관계로 대조하고, 변경 전 값을 조건으로 하는 바인딩 UPDATE와
  한 트랜잭션·행 수 검증을 검토한다. 이번 조사에서는 이러한 SQL을 실행하지 않았다.
- ID·관계·계정·비밀번호·설문·점수·좋아요·익명 번호·읽음 상태·시각을 보존한다.
  복구 직후 비텍스트 지문과 변경 행 수를 확인한 다음, 별도로 API/UI 동작을 확인한다.

## 이번 조사에서 수행·미수행한 작업

수행: 기존 문서·소스·Git/ref 이력·로그 읽기, 실제 프로세스/포트/DB 연결 조회,
두 DB의 읽기 전용 SELECT, 전시회 텍스트 303건 완전 비교, 백업 네 개의 파싱·체크섬 검증,
부작용 없는 공개 목록 GET 및 제공 중인 프론트 번들 확인, 새 조사 보고서와 증거 생성.

미수행: DB 변경·삭제·초기화, 시드 생성·apply·preview 실행, 백업 생성·복원·덮어쓰기·삭제,
서버 종료·재시작, Docker·서버·프론트 설정 변경, 로그인·상세 게시글 조회·채팅 읽음 처리.
상세 게시글 GET은 조회수 UPDATE가 있어 호출하지 않았다.
기존 `ApiCheck`/`BrowserCheck`도 로그인·읽음·조회수 변경을 일으킬 수 있어 다시 실행하지 않았다.
실행 환경 전환과 복원 리허설은 아직 하지 않았다. 미확정 정책을 새로 구현하지 않았다.

애플리케이션 소스 변경이 없어 전체 테스트/빌드는 실행하지 않았다.
계약 스냅샷 검사 `node backend/tools/sync-contract-docs.cjs --check`는
73 endpoints / 75 DTO / 30 entities 일치, `git diff --check`는 통과했다.

새 조사 도구/증거는 Git 제외 경로 `build/exhibition-investigation/`에 보존했다.
이번에 추가한 추적 대상 문서는 이 보고서 한 파일이다. 기존 실행기·시드·문서는 변경하지 않았다.

주요 증거 경로: `build/exhibition-investigation/evidence-20261031-235423/`.

- `processes.json`, `connections.json`, `recorded-server.json`: 실행 기록과 실제 프로세스 대조.
- `exhibition.jsonl`: 전시회 실제 닉네임·게시글·댓글·채팅 원문 projection.
- `development.jsonl`: 기존 DB와 실제 MySQL 연결의 조사 projection.
- `comparison.json`: 전체 대조 요약, 백업별 문구 차이·체크섬·TCP/MySQL 연결 매핑.
- `text-comparison.json`: 전시회 303건의 ID별 완전 일치 결과.
- `api-posts-utf8.json`, `api-roommates-utf8.json`, `public-api-comparison.json`:
  현재 공개 API와 기존 DB의 일치 및 프론트 API 주소 확인.

초기 수집기의 `api-posts.json`과 `api-roommates.json`은 Windows PowerShell의 응답 문자셋
해석으로 한글이 깨졌다. 판정은 Node fetch로 UTF-8 응답을 다시 읽어 저장한 `*-utf8.json`만 사용했다.
이 수집상의 문자셋 문제는 브라우저에서 옛 데이터가 보이는 원인과 무관하다.
