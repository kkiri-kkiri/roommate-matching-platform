# 커뮤니티 2번: 계정 상태와 쓰기 직렬화

## 원인과 변경

JWT 인증은 쓰기 서비스 트랜잭션 밖에서 USER를 일반 조회한다. 인증을 통과한 뒤
정지·탈퇴가 커밋되면 인증 결과만으로 이후 쓰기를 허용할 수 없다. 기존 게시글 작성은
프로필을 조회하고, 댓글 작성·좋아요는 사용자 존재만 확인하며, 수정·삭제·좋아요 취소도
쓰기 트랜잭션에서 계정 ACTIVE 상태를 잠금으로 보호하지 않았다.

CommunityPostService의 작성·수정(이미지 포함)·삭제·좋아요·취소 및
CommunityCommentService의 댓글/답글 작성·수정·삭제·좋아요·취소는 첫 DB 접근으로
기존 UserRepository.findByIdForAccountUpdate를 호출한다. 잠금 획득 후 ACTIVE가 아니거나
계정이 없으면 기존 UNAUTHORIZED를 반환한다. 기존 소유권 검사(FORBIDDEN), 콘텐츠 상태
검사(INVALID_REQUEST), 입력 검증과 API DTO는 유지한다. 계정 상태 검사가 먼저 수행되므로
비활성 계정이 잘못된 본문을 보내도 UNAUTHORIZED가 우선한다.

공통 계정 Repository는 getReference 후 refresh(PESSIMISTIC_WRITE)로 기존 영속성 컨텍스트의
오래된 상태도 갱신한다. 같은 트랜잭션에서 이미 잠근 계정은 다시 refresh하지 않아 아직
커밋하지 않은 상태 변경을 버리지 않는다. 이 구현과 기존 5초 잠금 힌트는 수정하지 않았다.
새 Version 필드·스키마·마이그레이션은 필요 없다.

## 호출 경로와 트랜잭션

Controller는 인증 Principal의 ID로 Service만 호출하며 Repository에 직접 저장하지 않는다.
모든 사용자 쓰기 진입점은 public @Transactional이며 Controller에서 Spring 프록시를 거친다.
private lockActiveUser는 이 트랜잭션 안에서 동작한다. 별도의 REQUIRES_NEW나 내부 호출에
의존하는 트랜잭션 선언을 추가하지 않았다. 댓글 쓰기 보조 서비스와 익명 번호 서비스의
MANDATORY 전파도 유지한다. 파일 롤백 동기화는 같은 트랜잭션에 등록된다.

신고 등록 ReportService.createReport는 이미 신고자 계정 잠금과 ACTIVE 검사를 수행한다.
POST/COMMENT 신고도 같은 규칙으로 보호되므로 중복 구현하지 않았다. 신고 등록은 대상
콘텐츠 상태를 변경하지 않는다. 관리자 신고 처리의 SUSPEND_USER는 대상 계정 잠금,
DELETE_TARGET은 기존 게시글 → 댓글 잠금을 사용하며 두 조치는 한 요청에서 함께 실행되지 않는다.

현재 본인 탈퇴 Controller/Service는 없다. WITHDRAWN의 실제 진입점은 관리자 회원 상태 변경이다.
AdminService.updateMemberStatus의 SUSPENDED/WITHDRAWN 전환은 기존 공통 계정 잠금을 사용한다.
JWT·UserService·관리자 서비스의 권한 정책이나 상태 전환 정책은 이번에 변경하지 않았다.

공개 상세 조회의 조회수 증가 및 과거 익명 번호 초기화는 공개 읽기 정책에 수반되는 작업이다.
요청자 계정 잠금을 추가하지 않고 기존 게시글 잠금과 조회수 증가 정책을 유지한다.

## 잠금 순서와 제한

| 작업 | 명시적 잠금 순서 |
| --- | --- |
| 게시글 작성 | 요청자 계정 → 새 게시글/이미지 저장 |
| 게시글 수정·삭제·좋아요 | 요청자 계정 → 게시글 → 필요한 이미지/댓글 |
| 댓글 작성 | 요청자 계정 → 게시글 |
| 대댓글 작성 | 요청자 계정 → 게시글 → 부모 댓글 |
| 댓글·대댓글 삭제 | 요청자 계정 → 게시글 → 대상 댓글 → 대댓글 ID 오름차순 |
| 댓글·대댓글 수정·좋아요 | 요청자 계정 → 대상 댓글 (게시글 잠금을 역으로 요청하지 않음) |
| 관리자 콘텐츠 삭제 | 게시글 → 댓글 (계정 잠금 추가 없음) |
| 관리자 정지·탈퇴 / 신고 정지 | 대상 계정 하나 |
| 신고 등록 | 신고자 계정 → 신고 저장 |

관리자 권한은 기존 일반 조회로 확인한다. 관리자와 대상 계정을 동시에 잠그는 변경은 없다.
따라서 이번 변경으로 다중 계정 잠금 순서를 만들지 않는다. 관리자 계정 자체의 정지와
관리 작업 권한 확인 사이의 경합은 이번 일반 사용자 쓰기 문제와 구분되며 기존 정책을 유지한다.

여러 댓글을 삭제할 때 기존 ID 순서를 유지한다. 익명 번호 초기화의 과거 이력 정렬은
기존 번호 정책을 위해 유지하며 게시글 잠금이 해당 다중 댓글 경로를 직렬화한다.
댓글 수정/좋아요는 단일 댓글만 잠그고 계정·게시글 잠금을 나중에 요청하지 않는다.

같은 계정의 쓰기는 서로 다른 게시글이어도 직렬화된다. 서로 다른 계정·게시글은 독립적으로
처리할 수 있다. 향후 여러 사용자의 쓰기를 하나의 외부 트랜잭션으로 조합한다면 전체 계정 ID를
오름차순으로 먼저 잠근 뒤 콘텐츠를 잠가야 한다. 이번 일반 Controller에는 그런 조합이 없다.

명시적 역방향 계정 잠금은 없지만 MySQL FK 검사에 의한 암시적 공유 잠금, 인덱스/GAP 잠금,
익명 이력의 지연 초기화, 다른 도메인의 트랜잭션까지 포함한 교착 부재를 보장하지 않는다.
잠금 실패는 전파되어 전체 트랜잭션을 롤백하고 기존 전역 처리기의 409 ACCOUNT_UPDATE_CONFLICT를
사용한다. 실패를 삼키거나 일부 저장만 커밋하거나 자동 재시도하지 않는다.

## 테스트 범위

신규 CommunityAccountConcurrencyIntegrationTest는 실제 Spring 서비스 프록시, JPA 독립
트랜잭션, H2 메모리 DB, 테스트별 임시 업로드 폴더를 사용한다. CountDownLatch로 선행
트랜잭션을 유지하고 H2 INFORMATION_SCHEMA.SESSIONS.BLOCKER_ID로 실제 잠금 대기를
관찰한 뒤 커밋한다. Thread.sleep이나 우연한 실행 순서에 의존하지 않는다.

- 게시글/댓글/대댓글 CRUD, 좋아요·취소, 익명 작성, 이미지 추가·제거·교체, 신고 등록:
  정지/탈퇴 각각에 대해 쓰기 선점과 상태 변경 선점 양쪽을 검증한다.
- 실제 JWT 인증 후 상태 변경 및 오래된 관리 User 엔티티가 남아 있는 경우의 거부.
- 비작성자 수정·삭제·이미지 수정 FORBIDDEN 및 DB/파일 불변.
- 계정 → 게시글/댓글 순서: 콘텐츠 잠금 대기 중 상태 변경도 계정 잠금에서 대기하는
  3개 독립 트랜잭션을 관찰한다.
- 계정 timeout으로 이전 DB 쓰기와 신규 파일이 모두 롤백됨을 확인한다.
- 관리자 삭제 및 신고 정지와의 경합, 다른 계정 독립 실행, 같은 계정 직렬화.
- 같은 트랜잭션에서 정지 후 재진입해도 상태를 ACTIVE로 갱신하지 않으며 전체 롤백.
- H2 REPEATABLE READ의 오래된 계정 snapshot 충돌은 잠금 예외와 전체 롤백으로 검증한다.
  정상 대기 후 최신 상태 검증은 H2 READ COMMITTED에서 검증한다.

기존 4·5번 테스트 중 독립 업로드는 서로 다른 계정·게시글로 수정했다. 같은 계정의 병렬
완료는 새 계정 직렬화 규칙과 충돌하기 때문이다. 기존 콘텐츠 timeout 테스트도 선행 쓰기의
작성자를 조정해 계정 잠금을 통과한 뒤 원래의 콘텐츠 timeout을 검증한다. 기존 테스트를
삭제하거나 개수를 줄이지 않았다. 1번 47개 테스트 코드는 유지한다.

## 배포 및 미검증

운영/공유 DB에는 접근하지 않았다. 실제 MySQL·다중 JVM 실행은 미실행이다.
격리된 MySQL에서 REPEATABLE READ의 current read, 잠금 힌트와 실제 lock wait timeout,
계정 → 콘텐츠 대기 사슬, FK 검사·익명 이력 초기화·신고 처리의 교착과 전체 롤백을 검증해야 한다.
H2의 기존 4·5번 RR 새 댓글 snapshot 제한도 해결했다고 주장하지 않는다.

구버전은 계정 잠금 없이 쓰므로 기존 쓰기 트랜잭션을 종료하고 모든 인스턴스를 같은 버전으로
전환해야 한다. 파일 I/O를 포함해 계정 잠금 유지 시간이 늘어나는 점을 부하 시험에서 확인한다.
3·6·7·8·9번은 수정하지 않는다. 이미지 keepImageIds 전체 교체 및 성공한 연결 제거 후
물리 파일 유지 정책도 그대로다.
